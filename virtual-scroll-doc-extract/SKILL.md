# 虚拟滚动富文档 · 完整内容提取

> 目标：把「我以为抓全了」变成「我能证明抓全了」。
> **核心认知：这类文档是「图文双载体」——正文文字和图片是两套并行内容，只抓文字会漏掉整章。**

## 0. 铁律

1. **先拿"分母"，再抓内容。** 钉钉/飞书文档侧栏或右上角有**字数统计**（如「7581 字」），这是唯一的核对基准。抓完必须比对：抓取长度与统计值同量级才算抓到。
   - ⚠️ 真实翻车：抓到 10008 字符就收工，结果文档还有**整整一章是以图片承载的**，纯文本永远拿不到 → 需求分析结论整体错了一个章节。
2. **`document.visibilityState === 'hidden'` 时 iframe 不渲染。** 后台标签里抓到的长度会**暴跌到几百字符**，且与滚动位置无关（表现为"怎么滚都是同一段"）。
   - 先激活窗口再抓：`osascript -e 'tell application "Google Chrome" to activate'`
3. **"撑高 iframe"治不了虚拟列表。** 把预览 iframe 的 height 设成 30000px / 120000px **只放大视口，不触发全量渲染**；且页面高度会跟着继续增长（渲染进度 ≠ 文档结尾）。撑到极端值反而会让内容崩成空白（实测 120000px → 内容只剩 535 字符）。
4. **"抓不到" ≠ "文档没写"。** 判定某章节是否为空，必须**截图看一眼**。截图有内容 + DOM 搜不到 = **图片承载**（`<img>` / canvas / CSS 背景图）。
5. **搜 DOM 要搜穿 Shadow DOM。** `TreeWalker` + 递归 `element.shadowRoot`，否则容易误判「NOT FOUND」。（实测会搜到 `WPS-TRANSLATE-ENTRY` 这类 18 万字符的 CSS 噪声，注意排除。）

## 1. 三步自检：这份文档我抓全了吗

```
① 前台渲染了吗？   document.visibilityState —— 'hidden' 就先激活 Chrome 重来
② 长度对得上吗？   len(body.innerText) vs 文档字数统计 —— 差一个数量级说明没抓全
③ 图片有几张？     document.querySelectorAll('img').length —— 0 也要警惕，可能是懒加载没触发
```

三条都过了，才允许下"已完整读取"的结论。

## 2. 抓正文（能拿到多少算多少）

1. `navigate` 打开文档 → `osascript` 激活 Chrome → 等 2s 让 iframe 渲染。
2. 正文在 iframe（钉钉是 `alidocs.dingtalk.com/note/preview?...`）里，取：
   ```js
   document.querySelectorAll('iframe').forEach(f=>{try{ ... f.contentDocument.body.innerText ... }catch(e){}})
   ```
3. 需要更多内容时**滚动收集**（比撑高可靠）：`scrollTop` 分屏推进，每屏取一次 `innerText`。
   - ⚠️ 虚拟列表分屏之间**没有行级重叠**，直接拼接会丢行 → 做不到无损就改用第 3 节的图片通道补齐。

## 3. 判定「空白章节」：截图 → 图片承载

当某章节 `innerText` 为空或只有标题时：

1. **先截图**该章节（`screenshot ref=...` 或滚动到位后整屏截）。**截图有内容 = 一定有需求，只是不在文字里。**
2. 确认不是 Shadow DOM 里的文字（搜穿后仍 NOT FOUND 即可排除）。
3. 把它当**图片承载**处理，走第 4 节。

> 这一步是整个 skill 的关键分叉点。跳过它就会得出"该章节未写需求"的错误结论。

## 4. 批量取出文档里的图片

1. **滚动扫描收集 URL**（懒加载必须边滚边收）：用 `scripts/collect_doc_images.js`。
2. **下载**：
   - ❌ `curl` 直接请求 → 返回 **0 字节**（没有登录态 / Referer 校验）。
   - ✅ 用浏览器通道下载：huashu-chrome 的 `fetch` 工具，参数带 `binary: true` + `savePath`，走当前标签的登录态。
3. 文件名按 **来源章节 + 顺序** 命名（`m_x0_1.png` = 第 M 组第 1 张），便于后续与章节对照。

## 5. 逐图解读（多模态读图，别只做 OCR）

- 用 `Read` 读图片（支持多模态），**重点看三类信息**：
  1. **流程图的分支与文案**（PRD 正文往往只写主干，分支条件只在图里）
  2. **页面字段与开关名**（常与正文叫法不一致 → 这就是冲突点）
  3. **图上的评审批注**（设计师/产品用红字标注的"二期""不做""维持原来"——**未闭环项**全在这里）
- 产出格式：**「图片清单表」+「逐图内容还原」+「新增/修正需求点汇总」**三件套，方便合并回主文档。

## 6. 图文核对：把"冲突"挖出来

正文与图片对同一件事的描述不一致，是本类文档最高价值的发现。逐项比对：

| 比对维度 | 典型冲突 |
|---|---|
| 数值 | 正文写 10 秒、图内正文写 15 秒、图内标题写 10 秒（三处不一致） |
| 行为界定 | 正文"仅能拨 SOS" vs 交互稿"禁止接听所有电话和消息" |
| 命名 | 正文"其他短信" vs 实拍"话费流量短信" |
| 结构 | 正文拆成两个章节描述 vs 交互稿是同一入口下两个开关 |

每条冲突按 **「症状 → 影响 → 需谁澄清」** 记录，并标注优先级（阻塞用例设计 / 影响范围判定 / 细节完善）。

## 7. 本机环境坑

- 沙箱设了 `HTTP_PROXY`，会连 `127.0.0.1` 一起代理（502）→ 命令行加 `--noproxy '*'`；Python 用 `build_opener(ProxyHandler({}))`。**代理端口每次会话不同，别写死。**
- Bash 的 `grep` 是 toybox，**多模式 `\|` 会静默返回空**（退出码 1，极易误判"该符号没被引用"）→ 用 `-E` 或专用检索工具。
- huashu-chrome 的 `eval` 是**单表达式**上下文（带分号的多语句会报 `Unexpected token ';'`）→ 用 IIFE 包裹：`(() => { ... return x; })()`。
- MasterGo 等设计稿是 **canvas 渲染**，取不到文本 → 只能截图 + 读图层名（图层名有时比 PRD 正文更细，如"2s内连续按5下"）。
